# Аудит бета-версии «Кухонная шпаргалка»

**Проверен URL:** `http://217.60.186.246/`  
**Статус доступа:** страница открывается и возвращает контент.  
**Покрытие аудита:** главная страница на основании доступного серверного HTML/текста. Для проверки реального визуального интерфейса, интерактивности, адаптива, консоли браузера и сетевых запросов нужны скриншоты, HAR или доступ по HTTPS-домену.

## Краткий вывод

Сайт уже отдаёт главную страницу: в ней присутствуют каталог рецептов и подборка кулинарных советов. Информационная архитектура на первом экране выглядит логичной: пользователь видит две основные сущности продукта — рецепты и советы.

Главные зоны роста для бета-версии: сделать карточки и навигацию более «находимыми», привести таксономию к единым словарям, исправить некачественно определённые аллергены и подготовить production-слой — HTTPS, SEO-метаданные, доступность и наблюдаемость.

## P0 — до публичного запуска

### 1. Перевести сайт с IP/HTTP на домен с HTTPS

**Наблюдение:** проверка выполнялась по `http://217.60.186.246/`.

**Почему это важно:** IP-адрес — плохой публичный адрес продукта: его сложно запоминать, он не формирует доверия, неудобен для canonical URL и может вызывать проблемы с внешними сервисами. HTTP не защищает трафик и данные форм.

**Правка:**

- Подключить домен и настроить DNS A/AAAA-записи на сервер.
- Выпустить TLS-сертификат в Caddy и включить HTTPS.
- Настроить постоянный 308/301-редирект с HTTP на HTTPS.
- Задать production URL одной переменной окружения, например `NEXT_PUBLIC_SITE_URL=https://example.ru`.
- В Next.js задать `metadataBase` и формировать абсолютные URL canonical/OG от домена.

**Критерий готовности:** `http://домен` перенаправляет на `https://домен`; браузер не показывает предупреждения; все канонические и Open Graph URL используют домен и HTTPS.

### 2. Исправить неопределённый аллерген у чизкейка

**Наблюдение:** у рецепта «Чизкейк без выпечки» в выдаче есть метка `неизвестно: яйцо` наряду с «глютен» и «молоко».

**Риск:** пользователю непонятно, содержит ли рецепт яйца, не удалось ли классифицировать ингредиент, либо данные повреждены. Для аллергиков такая неопределённость критична.

**Правка:**

- В модели данных заменить строковые/неопределённые значения на контролируемые enum-значения: `egg`, `milk`, `gluten`, `soy`, `sesame` и т. п.
- Развести состояния: `contains`, `may_contain`, `unknown`, `not_applicable`.
- Не выводить пользователю техническое значение `unknown: egg`; показывать понятный предупреждающий текст, если данных недостаточно: «Состав на яйца не проверен».
- Добавить в админскую валидацию: публикация рецепта невозможна, если у обязательной классификации есть `unknown`.
- Перепроверить ингредиенты и карточку этого рецепта вручную.

**Критерий готовности:** на пользовательской карточке отсутствуют технические статусы; все аллергенные метки подтверждены ингредиентами и имеют единый формат.

## P1 — заметно улучшит поиск и UX

### 3. Добавить явную навигацию и фильтры рецептов

**Наблюдение:** на главной представлены «Рецепты» и ссылка/действие «Все рецепты», а в карточках доступны признаки: тип продукта, способ приготовления, тип блюда и аллергены.

**Риск:** при росте базы пользователю будет трудно найти нужное блюдо: например, быстрый ужин без молока, десерт без духовки или рецепты из птицы.

**Правка:**

- Добавить поиск по названию и ингредиентам с debounce 250–350 ms.
- Добавить фильтры: категория блюда, основной продукт, способ приготовления, время, сложность, аллергены/исключения.
- Добавить сортировку: новые, популярные, быстрые, по времени приготовления.
- Отображать активные фильтры как chips с возможностью снять один фильтр или очистить всё.
- Сохранять состояние фильтров в query params, например `/recipes?course=dessert&exclude=milk`.
- На пустой выдаче показывать объяснение и действие «Сбросить фильтры».

**Критерий готовности:** пользователь может получить релевантную выборку за 2–3 действия и поделиться ссылкой с уже выбранными фильтрами.

### 4. Сделать таксономию единообразной и понятной

**Наблюдение:** данные карточек включают признаки наподобие «Яйца и молочные», «Птица», «Бобовые», «Варка», «На сковороде», «В духовке», «Закуска», «Основное блюдо».

**Риск:** сейчас смешиваются разные измерения классификации: ингредиент/группа продуктов, техника приготовления и тип приёма пищи/блюда. При расширении это ведёт к дублированию и непредсказуемым фильтрам.

**Правка:**

- Разделить сущности в модели: `ingredientGroups`, `cookingMethods`, `courseTypes`, `dietaryFlags`, `allergens`.
- Использовать справочники со стабильными slug: `poultry`, `legumes`, `oven`, `pan`, `main-course`, `snack`.
- Хранить отображаемые русские подписи отдельно от slug, чтобы изменение текста не ломало ссылки и фильтрацию.
- Определить правила множественности: у рецепта может быть несколько техник, несколько продуктовых групп и несколько типов блюда.

**Критерий готовности:** все теги попадают ровно в одну понятную группу, а выдача по каждому фильтру предсказуема.

### 5. Усилить карточку рецепта

**Наблюдение:** доступный контент карточек содержит название и теги, но из извлечённого текста не видно ключевых параметров выбора: время, сложность, порции, фото, краткое описание.

**Правка:**

- Добавить на карточку время приготовления, число порций и уровень сложности, если эти поля есть в данных.
- Добавить короткий description: 1–2 строки о вкусе/результате/поводе.
- Сделать кликабельной всю карточку при сохранении отдельной семантической ссылки на рецепт.
- Для аллергенов использовать не только цвет, но и текст или иконку с доступным названием.
- Если используется изображение, задать фиксированное соотношение сторон и резервирование места, чтобы не было layout shift.

**Критерий готовности:** пользователь может сравнить рецепты без открытия каждой карточки; на мобильном по карточкам удобно нажимать.

### 6. Сделать раздел советов предметно полезным для навигации

**Наблюдение:** советы имеют тематические рубрики, например «Варка, бульоны, супы и соусы», «Выбор мяса, рыбы и продуктов», «Выпечка и кондитерка», «Если что-то пошло не так», «Ножи, нарезка и инструменты».

**Правка:**

- Добавить фильтрацию по рубрикам и поиск по советам.
- На главной показывать 3–6 советов плюс заметную ссылку «Все советы».
- У каждой карточки добавить понятное действие: «Открыть совет» / «Читать полностью», если у совета есть развёрнутый материал.
- Связывать советы с рецептами и техниками: совет о жарке грибов — со страницей рецептов с грибами или техникой жарки.
- Использовать короткую структуру «проблема → причина → следующее действие», которая уже хорошо читается в текущем контенте.

**Критерий готовности:** посетитель может быстро найти совет по ситуации, а не только случайно прочитать его в общей ленте.

## P1 — доступность

### 7. Проверить семантику и доступность интерактивных элементов

**Наблюдение:** серверный текст показывает несколько однотипных действий «Все рецепты» и «Все советы», но по тексту нельзя подтвердить их HTML-реализацию.

**Правка:**

- Для переходов использовать `<a href="…">`, а не `div`/`span` с `onClick`.
- Для действий без навигации использовать `<button type="button">`.
- У каждого изображения рецепта задавать осмысленный `alt`, например: «Лазанья с мясным соусом и бешамелем»; у декоративных изображений — `alt=""`.
- Сделать видимое состояние `:focus-visible` для ссылок, кнопок, поля поиска, тегов-фильтров и мобильного меню.
- Не использовать цвет как единственный индикатор аллергенов, выбранных фильтров или ошибки.
- Сохранить логичную структуру страницы: один H1 «Кухонная шпаргалка», H2 «Рецепты» и H2 «Советы», H3 в карточках.
- Если есть модальные окна или drawer-фильтры, реализовать Escape, focus trap и возврат фокуса к кнопке-инициатору.

**Критерий готовности:** страница полностью проходится клавиатурой, а скринридер получает корректные названия и структуру.

## P1 — SEO и распространение

### 8. Добавить метаданные для главной, рецептов и советов

**Наблюдение:** в доступном текстовом представлении есть полезные заголовки, но нельзя подтвердить уникальные `<title>`, description, canonical, Open Graph и микроразметку.

**Правка:**

- Для главной задать содержательный title, например: `Кухонная шпаргалка — рецепты и практические советы`.
- Для карточек: `Яйца «Маяк» по-корейски — рецепт | Кухонная шпаргалка`.
- Уникально формировать `description` из описания, времени, кухни или ключевых ингредиентов, не переспамливая ключевыми словами.
- Настроить `metadataBase`, canonical URL, Open Graph `title`, `description`, `images`, `url`, `type`.
- Для рецептов добавить JSON-LD `Recipe` только по реальным данным: название, изображение, ингредиенты, рецепт, время, порции, автор; не выдумывать ratings/reviews.
- Сгенерировать `sitemap.xml` и `robots.txt` после подключения домена.
- На время закрытой беты использовать `X-Robots-Tag: noindex` либо Basic Auth/IP allowlist; после запуска убрать noindex осознанно.

**Критерий готовности:** у каждой публичной сущности свой indexable URL, метаданные и корректный предпросмотр при отправке ссылки в мессенджер.

## P2 — производительность и техническое качество

### 9. Зафиксировать режим кэширования публичного контента

**Наблюдение:** ранее основной ответ был динамическим и отправлялся с `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`; после оптимизации страница стала доступна автоматической проверке, но текущие заголовки и метрики нужно подтвердить отдельно.

**Правка:**

- Для публичных данных рецептов и советов использовать ISR/revalidation либо серверный cache, если контент не меняется на каждый запрос.
- Не использовать `cache: 'no-store'` для публичных справочных данных без обоснованной необходимости.
- Проверить, что вызовы `cookies()`, `headers()` и персональная авторизация не делают весь публичный маршрут динамическим.
- Параллелить независимые серверные запросы через `Promise.all`.
- Для секций ниже первого экрана применять streaming/Suspense там, где это не ухудшает UX.
- Оптимизировать изображения: современные форматы, корректные размеры, lazy loading ниже первого экрана, зарезервированное место под медиа.

**Критерий готовности:** холодный и повторный запросы измерены, TTFB стабилен; публичная главная не делает лишних синхронных запросов к API/БД.

### 10. Добавить наблюдаемость до роста аудитории

**Правка:**

- Логировать request ID, URL маршрута, HTTP-статус, время обработки в Caddy и приложении.
- Включить мониторинг исключений фронтенда и бэкенда.
- Собирать Web Vitals: LCP, INP, CLS и TTFB, раздельно для mobile/desktop.
- Отслеживать продуктовые события без персональных данных: поиск, применение фильтра, открытие рецепта, начало и завершение ключевого сценария.
- Настроить алерт на 5xx, резкий рост TTFB и недоступность главной.

**Критерий готовности:** проблему с медленной отдачей можно обнаружить по метрикам до пользовательских жалоб и связать с конкретным релизом/маршрутом.

- [ ] Главная, каталог, страница рецепта, каталог советов и страница совета имеют понятные URL и уникальные title/description.

- [ ] Работают поиск, фильтры, сортировка, состояние пустой выдачи и сброс фильтров.
- [ ] Сайт протестирован на 320/360/375/390/414/768/1024/1280 px, Chrome, Firefox и Safari/iOS.
- [ ] Нет горизонтального скролла, перекрытий, скачков интерфейса при загрузке и мелких tap targets.
- [ ] Сценарии проходят с клавиатуры; виден focus; семантика заголовков и ссылок корректна.
- [ ] Подключены HTTPS, редирект HTTP → HTTPS, домен, canonical, sitemap и robots.
- [ ] Включены мониторинг ошибок и сбор Web Vitals.

## Ограничения аудита

Этот отчёт основан на доступном содержимом главной страницы: рецептах, советах, категориях и аллергенных метках. Я не мог достоверно проверить визуальную композицию, CSS, наличие изображений, реальную кликабельность, клиентские ошибки, Lighthouse, мобильный layout, вложенные страницы, HTTP-заголовки после новой оптимизации и форму/авторизацию — их нет в извлечённом текстовом ответе.

Для второй итерации аудита стоит приложить HAR-файл или скриншоты главной, каталога и страницы рецепта в desktop/mobile. Тогда этот файл можно дополнить конкретными UI-дефектами с воспроизведением и привязкой к компонентам.
