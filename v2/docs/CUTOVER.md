# Cutover — чеклист на VPS

Операционный список. Стек и запреты не меняет: [ARCHITECTURE.md](ARCHITECTURE.md), числа — [DEFAULTS.md](DEFAULTS.md), DNS/домен — [PLAN.md](PLAN.md) §8 и [HUMAN.md](HUMAN.md) §7. Задача сессии — [../CURRENT_SPRINT.md](../CURRENT_SPRINT.md).

Первый публичный V2 — **read-only книга** на Timeweb, 8 ГБ RAM + swap 4, домен `sol-chef.ru`. Это не «неограниченный трафик» и не V2.1 (почта, оценки, фото). Аккаунты, Postbox, S3 — позже, когда человек скажет.

Два разных масштаба, не смешивать:

| | Реалистичный первый прод | «Сколько угодно» |
|--|-------------------------|------------------|
| Рецепты | сотни–низкие тысячи | десятки тысяч: SQL-выдача, не полный каталог в RAM |
| Визиты | один VPS, gunicorn 2 воркера | горизонталь, очередь, CDN — отдельное решение, не этот файл |

## 1. Продукт готов к публике (не инфраструктура)

Сайт должен быть тем, что обещает UX, без «скоро» и без дыр контента.

- [ ] Витрина `/`, калькулятор `/calculator`, книга `/recipes`, карточка `/recipes/<slug>`, крупы, мясо, советы — живые с Postgres.
- [ ] 301 `recipe.html?id=` → `/recipes/<slug>`.
- [ ] High-risk с блоком «Осторожно». `editorial_tested` только человек.
- [ ] Пустые ниши основы не показывают заглушку «скоро» (глава просто отсутствует).
- [ ] Формула «У меня» на карточке = Django (`ratio^0.7`), не V1 `0.5`.
- [ ] Калькулятор считает Django, не клиент.
- [ ] Принятые оверлеи в БД: после `import_v1` всегда `import_draft --accepted`. Повторный ETL не откатывает overlay.
- [ ] Регрессия V1: из корня `python -m http.server 3456` ещё открывает старый сайт, пока DNS на Pages.

Acceptance среза — [TESTING.md](TESTING.md) A1–A22. Прод не стартовать, пока локальный Compose не зелёный.

## 2. Код: выключить режим среза

Сейчас compose — разработка. В прод-образе этого быть не должно.

### Django

- [ ] `DJANGO_DEBUG=0`. Дефолт `1` в settings/compose — только локально.
- [ ] `DJANGO_SECRET_KEY` уникальный, не значение из `.env.example`.
- [ ] `DJANGO_ALLOWED_HOSTS` = `sol-chef.ru`, `www` если будет, внутреннее имя `backend`.
- [ ] `DJANGO_CSRF_TRUSTED_ORIGINS` = `https://sol-chef.ru` (и www).
- [ ] gunicorn в зависимостях backend (`pyproject.toml`). Сейчас пакета нет, в Docker — `runserver`.
- [ ] Прод-команда: `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 2` ([DEFAULTS.md](DEFAULTS.md)). Не `runserver`.
- [ ] WhiteNoise отдаёт `/static/` админки (уже в middleware).
- [ ] `CONN_MAX_AGE` или пул к Postgres: 2 воркера не открывают новое соединение на каждый запрос вхолостую.
- [ ] Bind-mount исходников с хоста в прод-compose нет. Код внутри образа.

### Next

- [ ] Прод-команда: `next build` в CI, в контейнере `node server.js` из `output: 'standalone'` (уже в `next.config.ts`). Не `npm run dev`.
- [ ] `NODE_ENV=production`.
- [ ] `INTERNAL_API_URL=http://backend:8000`. `NEXT_PUBLIC_API_URL` пустой.
- [ ] Главная / книга / калькулятор не обязаны быть `force-dynamic` навсегда. Публичное тело можно ISR; персональное (когда появится) — клиентский `/api/` после гидрации.
- [ ] Таймаут SSR к Django больше 8 с *или* эндпоинты быстрее 8 с. Сейчас `FETCH_MS = 8000` в `lib/api.ts` — при полном каталоге в RAM главная и книга отвалятся.

### Compose / Caddy на VPS

- [ ] Отдельный prod-файл (или overlay): без bind-mount, без `uv sync` на старте, без `npm install` на старте.
- [ ] На хост с VPS торчит только 80/443 Caddy. Postgres, Redis, 8000, 3000 — Docker-сеть.
- [ ] HTTPS (Let's Encrypt / Caddy). Внутренние сервисы HTTP.
- [ ] `/_internal/*` снаружи 404. Revalidate — только из сети Docker, HMAC.
- [ ] Webpack HMR в прод-Caddyfile нет.
- [ ] TZ `Europe/Moscow` на всех сервисах.

## 3. Каталог любого размера (код до DNS)

Postgres не ограничивает число `Recipe`. Узкие места — импорт V1 и чтение всего каталога в память.

### Снять «ровно N» там, где это про таблицу, не про снимок V1

- [ ] `import_v1` не проверяет `Recipe.objects.count() == 43`. (Снято 2026-09-07.)
- [ ] `EXPECTED_RECIPE_COUNT = 43` и `EXPECTED_RECIPE_FILES = 19` остаются **только** сверкой корневого JSON V1. Новые блюда — `import_draft`, не правка этих констант.
- [ ] `EXPECTED_CONTENT_DOCUMENTS = 5` — пока справочников пять. Новый гид (рыба и т.п.) = миграция контента + правка константы **до** деплоя, иначе контейнер не стартанёт.
- [ ] `RECIPE_TAXONOMY` и `v1_ingredient_map.json` — только ETL корня. Overlay-slug туда не обязаны попадать.
- [ ] В [TESTING.md](TESTING.md) I2/A3 формулировка «count остаётся 43» — про снимок V1, не про размер прод-БД.

### Не тащить весь каталог в RAM

Сейчас так: `/api/recommendations/` делает `list(qs)` и `solve_recipe` по каждому published; книга без поиска берёт `results` целиком; главная тянет всё, чтобы выбрать 6 случайных.

- [ ] Каталог `/api/recipes/`: пагинация **в SQL**, не `list(qs)` потом page 20. Фильтр `without=` — в запросе или предрасчитанном поле аллергенов, не цикл Python по всем строкам.
- [ ] Книга `/recipes`: оглавление и глава не требуют полного массива recommendations. Счётчики глав — `GROUP BY` / отдельный лёгкий эндпоинт.
- [ ] Главная: 6 случайных — `ORDER BY random() LIMIT 6` (или ротация в Redis), не «скачать все и выбрать».
- [ ] Калькулятор `/api/recommendations/`:
  - жёсткий отсев (unpublished, аллерген, нет основы) в SQL;
  - `solve` только по кандидатам, не по всей книге;
  - в JSON доски — featured + buckets, не полный `results` на тысячи карточек;
  - потолок кандидатов или отсечение по score **после** SQL-фильтров (продуктово согласовать, не молча выкидывать «сейчас»).
- [ ] Прогнать pytest калькулятора и e2e E1–E4, E11, E17–E21 после этой правки.

Ориентир: 200–500 рецептов на 8 ГБ ещё можно «в лоб». 2–5 тысяч без пунктов выше — главная и калькулятор будут упираться в 8 с и CPU.

## 4. Данные и импорт на сервере

- [ ] Прод-старт контейнера: `migrate` + `collectstatic`. **Не** `import_v1` на каждый reboot.
- [ ] Импорт — отдельная команда/job в CI или ручной one-shot: `import_v1` затем `import_draft --accepted`.
- [ ] Бэкап Postgres до импорта и после. Том не единственная копия.
- [ ] Повторный импорт идемпотентный (upsert по slug). Overlay не затирается.
- [ ] В проде нет `_terra/`, `_repass*.py`, pytest cache, `.venv` в образе (dockerignore).
- [ ] Расширения Postgres: `pg_trgm`, `unaccent`, функция `normalize_ru` — в init, не руками на хосте.
- [ ] Redis AOF on, но сессии только в Postgres.

## 9. Наблюдаемость, бэкапы, нагрузка

На 8 ГБ нет отдельного APM-стека в каноне. Минимум:

- [ ] Логи Caddy / gunicorn / Next крутятся, не забивают диск.
- [ ] Бэкап Postgres по расписанию (том + выгрузка наружу). Проверить restore на копии.
- [ ] Алерт: контейнер unhealthy, диск, RAM.
- [ ] Смоук после деплоя: `/`, `/recipes`, `/calculator`, один эталон (`barhatnaya-govyadina-po-kitajski`), `/api/recipes/?page=1`, `/healthz`.

Нагрузочный минимум до DNS (локально или staging):

- [ ] 50 параллельных GET `/` и `/recipes` — p95 < таймаута SSR.
- [ ] 20 параллельных `/api/recommendations/?have=beef_mince` — ответ доски, не 502.
- [ ] Каталог `count` в API = число published в БД, не 43.

## 12. Когда этот VPS станет мал

Не делать заранее. Триггеры:

- RAM gunicorn+Next+Postgres стабильно > ~6 ГБ из 8.
- p95 `/api/recommendations/` или `/recipes` > 2–3 с на обычном вечернем трафике.
- Published рецептов больше ~2–3 тысяч при выдаче «весь каталог».

Тогда, отдельно от cutover: больше воркеров только если RAM позволяет; вынести Postgres; CDN на статику Next; очередь не для read-only книги. Не ставить ClamAV и не собирать образы на этой машине.
