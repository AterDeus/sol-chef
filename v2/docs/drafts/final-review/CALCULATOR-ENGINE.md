# Калькулятор sol-chef 2.0 — логика движка для аудита

Снимок кода на 2026-09-20, каталог ~255 семейств. Канон продукта: [`v2/docs/CALCULATOR.md`](../../CALCULATOR.md). Веса чисел: [`v2/docs/DEFAULTS.md`](../../DEFAULTS.md) и `settings.RANKING_WEIGHTS`. Этот файл — **как работает код**, со всеми развилками. Если канон и код расходятся, для аудита верить коду; расхождения собраны в §19.

Не путать с масштабированием порций на карточке рецепта («У меня» / `servings`). Калькулятор **не** масштабирует граммы и **не** проверяет, хватает ли количества — только факт канонического id.

Цель аудита: полный контур, дыры смысла, идеи ускорения. Менять ранжирование (U15–U22, веса, ядро) — только решением человека.

---

## 1. Задача продукта

Человек сообщает ситуацию: что есть дома и/или что сейчас важнее. Система не ищет по названию и не вызывает LLM. Django собирает **одно решение на семейство** (slug + оси + замены + покупка + «почему») и отдаёт витрину: одно главное блюдо и до трёх альтернатив.

Ответ API — не каталог. Это `featured` + `alternatives` + служебные `buckets` / `results`. Полный пул живёт только внутри запроса.

Книга (`/recipes`, `GET /api/recipes/`) — другой эндпоинт. Главная витрина солвер **больше не зовёт** (случайные 6 из каталога).

---

## 2. Поверхности и кэш

| Слой | Путь | Когда солвер |
|------|------|----------------|
| Экран | `GET /calculator?...` | Только если в URL есть ключ из `FILTER_KEYS` |
| API | `GET /api/recommendations/?...` | Только если query «спросили»; пустой — idle, каталог не грузится |
| Словарь чипов | `GET /api/ingredients/` | Экран всегда (`fetchPantryOptions`) |

Ключи экрана (`v2/frontend/lib/filters.ts`):  
`have`, `have_group`, `intent`, `protein_base`, `cook_method`, `dish_type`, `equipment`, `without`.

Фронт:

- `dynamic = 'force-dynamic'` — HTML не ISR.
- Форма — обычный GET, без SPA.
- Пустой `/calculator` солвер **не** зовёт, только чипы и подсказку.
- Если в URL что-то есть — форма рендерится сразу, доска в `Suspense` (fallback «Подбираем блюда…»).
- Повтор того же query: Django locmem 45 с; Next `revalidate: 60` поверх. После импорта доска может быть старой до 45 с.

Неизвестный код VOCAB / неизвестный продукт → HTTP 400, русский `detail`. Не тихий skip.

Компонент `SolutionBuckets` (три сетки «сейчас / почти / лучше») в коде есть, **экран калькулятора его не рендерит**. Человек видит только `SolutionBoard`. Корзины остаются в JSON.

## 3. Параметры запроса

Парсер: `v2/backend/apps/recipes/query.py`. Повторы `?have=a&have=b` или CSV `?have=a,b`. Один ключ — OR, разные ключи — AND.

### 3.1. `have` — конкретные продукты

Канонические id супермаркета (`pantry_vocab`, не `protein_base`) или русские алиасы `HAVE_TEXT_ALIASES`.

- `свинина` → группа свинины, не один отруб.
- Голое «масло» не резолвится (многозначно).
- Фраза с пробелами: longest-match по словам (`resolve_pantry_text`).
- Неизвестное слово → 400.

Явный список после parse копируется в `explicit_have`. Дальше в рабочий `have` дописываются группы.

### 3.2. `have_group` — грубые чипы

Коды `HAVE_GROUPS` (UI-первый ряд: `chicken`, `meat`, `fish`, `veg`, `grains`, `eggs`, `dairy`, `other`; плюс виды `pork` / `beef` / `lamb` / `offal` и др.). Каждая группа → фиксированный список канонических id.

Два независимых «не раскрывать лишнее»:

1. `groups_to_expand`: родитель `meat` **не** раскрывается, если уже выбран ребёнок (`beef` / `pork` / `lamb` / `offal`). Иначе «говядина» тащит всю свинину. Замок **U21**.
2. В `RecommendationListView`: если среди явных `have=` уже есть id из этой группы — группа целиком не дописывается (человек уточнил отруб).

Раскрытые id группы участвуют в **матче** ядра. В `explicit_have` они **не** входят. Бонус «из всего выбранного» и счётчик `have_used` — только по токенам `have=`.

### 3.3. `intent` — сценарий, не жёсткий фильтр

Коды: `fast`, `pantry`, `oven`, `light`, `easy`, `batch`. Несколько — все применяются как **надбавки/штрафы** к баллу, блюдо из-за intent **не выкидывается**.

Это расходится с таблицей DEFAULTS («fast = time ≤ 30 иначе отсев»). Живой код — §9.3.

### 3.4. Оси каталога (жёсткий SQL, потом ещё раз на комбо)

| Query | SQL (`_apply_filters`) | Повтор на комбо (`combo_fits`) |
|-------|------------------------|--------------------------------|
| `protein_base` | база **или** `protein_bases_extra` overlap **или** addon `has_delta` + `protein_base_override` | итоговые базы комбо ∩ фильтр |
| `cook_method` | база **или** equipment-вариант с `cook_method_override` | итоговый method комбо |
| `equipment` | база **или** equipment-вариант `has_delta` с этим кодом посуды | итоговая посуда комбо |
| `dish_type` | `dish_type` семьи | только SQL; на комбо не режет, но даёт балл |
| `cuts` | `allowed_cuts` overlap | только SQL |
| `without` (алиас `exclude_allergen`) | Python после SQL: `catalog_allergens` — `contains` **или** `unknown` | `may_contain` не отсекает; optional-строки в аллергены карточки не входят |

Неопубликованные не входят. `kcal_max` / диета / бюджет / pairing в солвер не идут.

`dish_type` и `cuts` **не** включают режим explore (§5). Они только сужают SQL.

Аллергены карточки — худший случай по addon-дельтам, без `optional`.

## 4. Пайплайн одного API-запроса

`RecommendationListView.get` → для каждой семьи `solve_recipe` → сортировка семей → корзины → доска.

```
query
  → parse (400 если мусор)
  → published + prefetch ingredients/steps/variants
  → SQL-фильтры осей
  → Python-отсев without
  → substitution rules (только если have непустой)
  → для каждой семьи:
        перебрать осевые комбо
        assemble_recipe(..., enrich=False)
        combo_fits? иначе skip
        match_pantry (если have)
        score + why
        оставить ОДНО лучшее комбо семьи
  → отсортировать семьи
  → assign_buckets
  → build_board: 1 featured + до 3 alternatives
  → JSON
```

`enrich=False`: оси и состав после дельт, без nutrition-SELECT. Аллергены карточки всё равно из JSON семьи (худший случай), не из выбранного комбо — в `CookingSolution.allergens` лежит `catalog_item`.

Главная цена CPU: deepcopy состава/шагов в `assemble` на **каждое** комбо каждой семьи. Арифметика балла дешёвая.

## 5. Оси семейства (вариант 2)

Модель: `RecipeVariant` (`axis` = `addon` | `equipment`). В перебор идут только `has_delta=true`. Чип без дельты состав не меняет и в комбо не входит.

**Explore** включается, если непусто хотя бы одно из: рабочий `have` (включая раскрытые группы), `cook_method`, `equipment`, `protein_base`, `intent`.

- `explore = false` (пустой API, либо только `dish_type` / `cuts` / `without`): одно комбо — домашняя база, `(addon=None, equipment=None)`. Чипы не перебираются.
- `explore = true`: декартово произведение  
  `{None} ∪ addon-дельты` × `{None} ∪ equipment-дельты`, затем `combo_fits`.

Итог комбо после `assemble_recipe(variant_code, equipment_code)`: `protein_base` (с override чипа), `cook_method` (с override посуды), `equipment`, состав и шаги уже с дельтами.

`combo_protein_bases`: если addon с `protein_base_override` — только этот код; иначе `[recipe.protein_base] + protein_bases_extra`.

На доску из семьи попадает **одна** строка. Куриная шаурма и говяжий чип той же шаурмы не стоят рядом как featured + альтернатива: альтернативы режутся по `slug`, не по осям. Выбранный чип — тот, что выиграл внутри семьи (U15 / U15b).

Ничья внутри семьи (ключ меньше — лучше):

```
(-have_all, -have_used, -score, missing, число замен, штраф addon, штраф посуды, title)
```

`штраф addon/посуды` = 0 для базы, 1 для дельты. При равном балле побеждает домашняя ось.

## 6. Что такое ядро

`is_core_line` в `solve.py`, не «все строки состава».

Строка **не** ядро, если:

- `optional` (по желанию / для подачи),
- класс наличия `assumed` / `common` / `exotic`,
- единица `pinch` или `tsp` **и** нет `is_anchor`.

Иначе ядро. `is_anchor` бьёт pinch: якорь «по вкусу» докупается. Нет `canonical_id` — **не** ядро.

Классы (`availability_class`):

| Класс | Кто | В солвере |
|-------|-----|-----------|
| `assumed` | вода, соль, крупная соль, сахар, чёрный перец, растительное масло (`PANTRY_ASSUMED`); плюс `PANTRY_LEGACY_OR` | Не ядро, всегда «есть» |
| `common` | паприка, лавр, зира, соевый… | Не ядро. Нет в `have` → список `desirable`, в why «желательно …, но можно без этого». Не missing, не штраф |
| `exotic` | `PANTRY_EXOTIC` | Не ядро, молча |
| `explicit` | остальное с id | Кандидат в ядро (если не optional/pinch) |

Редакционный «шкаф» карточки рецепта (лимон, уксус, ложка муки) **шире** assumed и в солвер сам не подмешивается.

Строка без `canonical_id`, не pinch/tsp и не optional, проходит как ядро. `cover_need` её почти никогда не закроет → попадёт в «докупить» с пустым id. Стоит аудитору.

Граммы кладовки — не этот спринт.

## 7. Замены

`SubstitutionRule`, сид `substitution_rules.json`. Рантайм-LLM запрещён.

Направление: `from` = чего хочет рецепт, `to` = что есть у человека.

Правила этого slug перекрывают глобальные пары `(from, to)`.

Подставить: `to` ∈ `have`, `forbidden=false`, `quality ≥ 0.50`. Из кандидатов — max quality.

Прямое совпадение id: quality 1.0, трения нет.

Замена закрывает ядро (не missing), но −3 за каждую (`substitution_friction`) и строка в why `вместо {from} — {to}`.

`intent=pantry` в коде **не** запрещает замены. Он только даёт +12, если `missing==0` (ядро закрыто, замены разрешены), иначе −3 за каждую missing-строку. Это расходится с формулировкой «pantry = без замен» в старых кусках DEFAULTS.

## 8. Матч кладовки (`match_pantry`)

Если рабочий `have` пуст: shopping/substitutions/desirable пустые, `hits=missing=0`, pantry-веса = 0. Семья живёт на баллах осей, editorial и intent.

Если `have` непуст — по каждой строке состава выбранного комбо:

1. `common` и не optional → desirable, если id нет в have; дальше не смотреть.
2. Не ядро → skip.
3. `cover_need` → нет: в `shopping` (докупить). Есть / замена: `hits += 1`, id нужды в `covered_ids`; в `used_have` кладётся и need, и `to`, если они в have.

`missing` = длина shopping = число непокрытых **ядровых** строк.

`have_used` в решении — **число**, не список: `|used_have ∩ explicit_have|`. Группы не считаются.

`have_all` = `explicit_have` непустой и каждый его id ∈ `used_have`. Два и больше явных продукта + `have_all` → +16 и `why`: «из всего выбранного». Один явный продукт, даже если он весь использован, +16 не даёт. Замок **U21**.

Блюдо с `hits == 0` при непустом have на доску **не** попадает (корзина `rest`, `build_board` его не берёт). Стейк при фарше, взбитое масло без мяса — пустая роль. Если ни одна семья не взяла «Есть» → `featured: null`. Замок **U20**.

Частичное покрытие (1 из 3 ядровых) живёт: корзина `almost` или `best`.

## 9. Балл

Целое. Пользователю не показывать. Сумма четырёх кусков:

```
chip_score + pantry_score + intent_pts + protein_pts
```

Жёсткий SQL-отсев балла не даёт: семьи просто нет.

### 9.1. Чипы осей (`score_and_why`) — только если фильтр задан

| Условие | Балл | Why |
|---------|------|-----|
| `protein_base` задан и код есть в базах комбо | +10 | `основа — {метка}` |
| `cook_method` задан и совпал | +4 | `совпал метод` |
| `dish_type` задан и совпал | +2 | `совпал тип блюда` |
| `equipment` задан и совпала посуда | +2 | `совпала посуда — {метка}` |
| `editorial_tested` | +4 | `проверено редакцией` |

Если комбо — не домашняя ось, `axes_why` подменяет общие фразы на «{Говядина} — вариант», «духовка — вариант посуды», «посуда — казан (вариант)» и выкидывает дубли «основа —» / «совпал метод» / «совпала посуда».

Без фильтра по оси бонус оси = 0.

### 9.2. Кладовка (`pantry_score`, только при непустом have)

| Условие | Балл | Why (`pantry_why`) |
|---------|------|---------------------|
| каждая покрытая ядровая строка | +2 | не построчно; см. ниже |
| каждая missing | −20 | в why сводка, не «надо X» на каждую |
| каждая замена | −3 | `вместо A — B` |
| missing == 0 | +10 | `можно приготовить сейчас` |
| missing == 1 | — | `нужно докупить: {имя}` |
| missing ≥ 2 | — | `нужно докупить: a, b, c и ещё N` (первые три) |
| есть desirable | 0 | `желательно: …, но можно без этого` |

`have_all` и ≥ 2 явных: +16, «из всего выбранного» (кладут в `intent_pts`, не в pantry_score).

### 9.3. Intent (`intent_adjust`) — мягкий

Никто не вылетает. Можно получить отрицательный intent и всё равно попасть на доску, если кладовка сильная.

| Код | Эффект |
|-----|--------|
| `fast` | способ `pan_fry` / `no_cook` / `grill` **+8** и why «быстрее на плите»; `stew` / `oven` **−3**; всем **−min(шагов, 6)** |
| `oven` | итоговый method `oven` **+10**, why «духовка» |
| `light` | только если `recipe.energy_profile == "light"`: **+8**, «полегче по составу». Богатые блюда не режутся. Не ккал. |
| `fast` + минуты | **−min(total//15, 6)**; why «быстрее по времени» если ≤ 30. Нет минут — этот кусок молчит |
| `easy` | **−min(шагов, 8)**; если method `oven` / `stew` / `no_cook` **+4**, «меньше стоять у плиты». Поля `skill` нет |
| `batch` | method `stew` / `oven` **+8**, «можно на несколько дней». `servings` не смотрит |
| `pantry` | отдельно после adjust, только если have: missing==0 → **+12** «из того, что есть»; иначе **−3 × missing** |

«Быстро» в UI — не 15/30 минут: `time_total_minutes` в солвере не читается.

### 9.4. Белок из кладовки (`protein_from_pantry`)

Только если have непуст **и** `covered_ids` непуст. Бонус только когда ядровая строка закрыта (фарш не закрывает стейк).

Порядок:

1. Если в покрытом ядре есть свежая рыба (`FISH_FRESH`) **и** основа комбо ∈ `FISH_PROTEIN` → **+8**, «есть рыба».
2. Иначе если есть консервы (`FISH_CANNED`), нет свежей, основа рыбная → **+3**, «есть рыбные консервы».
3. Затем **один** (break) бонус **+6** по первому совпавшему из порядка групп: chicken → pork → beef → lamb → eggs → veg → legumes → meat. Условие: пересечение `covered ∩ HAVE_GROUPS[group]` непусто **и** основа комбо ∈ `HAVE_GROUP_PROTEIN[group]`. Why: `есть {метка первого id по sort}`.

Рыбный +8/+3 и мясной +6 теоретически оба могут сработать, если основа комбо одновременно в `FISH_PROTEIN` и в мясной группе — в текущем VOCAB так не бывает. Два отруба одной группы не суммируются (break). Курица в ядре говяжьего блюда бонуса не даёт: основа не из группы курицы.

Масло / assumed / непокрытый стейк — 0. Замок **U20**.

## 10. Сортировка семей (после выбора лучшего комбо)

С непустым have:

```
(заготовка?, -have_all, -have_used, -pantry_hits, -score, title)
```

Без have:

```
(заготовка?, -score, title)
```

`заготовка?` = 1 если `dish_type` ∈ {`sauce`, `preserve`}, иначе 0. Масло ниже любого блюда.

---

## 11. Корзины (`assign_buckets`)

Только при непустом have. Без have все `bucket="match"`, в JSON корзины пустые.

Семья с `hits <= 0` → `rest`, в доску не идёт (не now/almost/best).

| Корзина | Условие | Лимит |
|---------|---------|-------|
| `now` | hits > 0 и missing == 0 | нет |
| `almost` | hits > 0 и missing ∈ {1, 2} | нет |
| `best` | hits > 0 и missing ≥ 3 | первые 5 после сортировки `_board_sort` |
| `rest` | hits == 0 или хвост best | не на доске |

`now` **разрешает замены**: missing==0 значит ядро закрыто (есть или заменой). Это не «без трения». Трение видно в why и в −3.

Заготовка с hits>0 может попасть в now — но доска её выкинет, пока есть еда.

---

## 12. Доска (`build_board`)

Не «топ-N по баллу» и не три сетки.

1. Пул при have = `now + almost + best` (уже без hits=0). Без have = все solutions.
2. Если в пуле есть `is_standalone_dish` (не sauce/preserve) — пул = только они. Если пул одни заготовки (человек спросил `dish_type=sauce`) — заготовки остаются. **U22**.
3. Без have пул обрезается до **8** перед выбором featured.
4. Featured: если в пуле кто-то с `have_all` — лучший из них по `_board_sort`; иначе первый элемент пула.
5. Альтернативы — другие **slug** (не другие оси той же семьи), до трёх, жадным `take` в порядке пула:

| Подпись | Первое блюдо, для которого |
|---------|----------------------------|
| **Быстрее** | `total_minutes` заданы у обоих и у альта строго меньше |
| **На плите** | method ∈ {`pan_fry`, `no_cook`, `grill`} |
| **В духовке** | method == `oven` |
| **На несколько дней** | method == `stew` |
| **Ещё вариант** | добивка, пока нет трёх |

«Быстрее» — только если `total_minutes` альта строго меньше, чем у featured. Нет минут — не врать. Иначе «На плите» / «В духовке» / «На несколько дней».

Экран: «Я бы приготовил» + why + докупка/замены словами + «Ещё варианты» с тегом. `score` не рисуется. Минуты на featured — из `time_profile` решения после assemble; пустые не выдумывать.

Клик: `/recipes/<slug>?variant=&equipment=` из `applied_axes`. Состав карточки должен совпасть с обещанием (assemble тех же осей).

`results` при have = now+almost+best (может быть больше, чем 1+3 на экране). Без have = featured + три альта. `buckets` в JSON для отладки.

## 13. Чего калькулятор не делает

- Не полнотекстный поиск (`q=` — книга).
- Не планировщик недели (`/prep`).
- Не считает КБЖУ решения (кроме мягкого бонуса `energy_profile=light`).
- Не проверяет количества, сроки, бюджет, диету, парность.
- Не вызывает модель в запросе.
- Не подставляет `PANTRY_COMMON` молча как «есть».
- Не показывает unpublished.
- XOR / `choice_group` в JSON рецепта **не читает**: обе ветки, если обе обязательные строки, видит как ядро. Вторая ветка должна быть addon-дельтой или substitution.
- Не плодит несколько карточек одного slug на доске.

## 14. Производительность (локальный срез, 2026-09-20)

Узкое место больше не deepcopy на запросе. Rank читает `axis_snapshots`; состав собирается при импорте/`rebuild_axis_snapshots`. ORM солвера — published + variants, без steps (ингредиенты — только если `without=`). Пустой API не трогает каталог.

Смоук `:8080` после этапа 3:

- пустой `GET /api/recommendations/` ~6–45 мс (было ~1.2 с);
- `have_group=chicken&intent=fast` первый ~100 мс, повтор (locmem 45 с) ~21 мс;
- HTML `/calculator?have_group=…&intent=…` ~115 мс TTFB (было ~1.8 с).

На ВМ `217.60.186.246` этап 3 выложен без push `main` (migrate `0010` + 255 снимков). С самой ВМ пустой API ~8 мс; снаружи `have_group`+`intent` первый ~0.80 с, повтор ~0.24 с.

Почему нельзя «сначала семьи, у которых protein_base ∈ have»: покрытие считается **по строкам ядра**. Стейк и фарш — разные id. Предфильтр по основам сломает U20.

Уже в коде, формулу не меняет:

- предрасчёт на импорт/save: ядровые id, аллергены комбо, method, equipment, step_count, минуты;
- rank по снимкам; нет снимка — запасной assemble;
- кэш ответа Django locmem 45 с по каноническому query;
- Suspense на доске;
- не звать солвер с главной и из книги.

## 17. JSON решения (факт serialize)

Отдаётся: slug, title, protein_base, protein_bases (чипы **семьи**, не только выбранного комбо), protein_variants, cook_method, dish_type, equipment, allowed_cuts, applied_axes `{variant, equipment}`, bucket, why[], score, shopping_delta[], substitutions[], allergens **комбо**, high_risk_flags комбо, has_delta_variants, step_count, `time_profile` {total, active}.

Не отдаётся, хотя считается: `have_used`, `have_all`, `pantry_hits`. Альтернатива дополнительно получает `label`.

`protein_bases` на карточке решения — семейные чипы из list-item, поэтому UI может показать «ещё основы», даже если featured уже конкретный override.

## 18. Вопросы аудитору (не решения)

1. Предрасчёт ядра по осям vs deepcopy — где сломается эквивалентность (optional, pinch, строки без id, XOR, common/desirable)?
2. `intent` мягкий: `fast` не режет часовое тушение, только штрафует. Так и задумано (канон CALCULATOR) или дыра относительно ожидания «быстро»?
3. `intent=pantry` разрешает замены (+12 при missing=0). Нужен ли запрет замен, как в старом DEFAULTS?
4. `intent=light` смотрит `energy_profile`, не ккал порции. Поле у многих `standard` — сценарий почти не работает.
5. Несколько белков в ядре: +6 только первой группе из фиксированного порядка. Рыба отдельно +8/+3.
6. Одна строка на slug: говяжий чип выиграл — куриный домашний на доске не виден. Ок?
7. `explore=false` при одном `dish_type` не перебирает чипы — «суп» без основы не откроет говяжий вариант куриного семейства.
8. `PANTRY_COMMON` только «желательно». Exotic молча. Достаточно ли это против сюрприза «в составе лайм»?
9. Строки без canonical_id как ядро — баг?
10. Next cache 60 с vs свежий импорт.
11. Пустой recommendations API: нужен ли вообще, если экран без query его не рисует?
12. Подпись «Быстрее» ≠ корзина now ≠ меньшее `time_total_minutes`. Путает ли копию?
13. `have_group` никогда не даёт +16 «из всего выбранного».
14. Что отсечь до assemble, не нарушив U20: intent не кандидат (мягкий); пересечение снимка ядра с have — да, если снимок верный.
15. Аллергены на решении — худший случай семьи, не выбранного комбо. Чип без молока может показать молоко.

## 19. Канон vs код (чтобы аудитор не спорил с DEFAULTS)

| Тема | Канон / DEFAULTS | Код 2026-09-20 |
|------|------------------|----------------|
| Intent | CALCULATOR: вес, не обязательный способ. DEFAULTS ещё описывает жёсткий отсев (≤30 мин, skill, ккал&lt;500, servings) | Только мягкие ±, см. §9.3. `fast` читает минуты комбо, skill по-прежнему нет |
| `intent=pantry` | «ядро без замен» в старых весах | +12 при missing=0, замены ок; копирайт «с заменой», если substitutions |
| Why кладовки | DEFAULTS: «сейчас» / «есть строка» / «надо строка» | «можно приготовить сейчас» / сводка докупки / «желательно» |
| Why have_all | «все продукты» | «из всего выбранного» |
| Несколько комбо на доске | старые черновики перебирали все и клали несколько ключей | одна семья — одна строка |
| Главная | CALCULATOR ещё пишет, что витрина берёт пустой recommendations | Главная — `sample=6` каталога |
| «Быстрее» | раньше = второе блюдо из корзины now | только если `total` альта строго меньше featured; иначе «На плите» / «В духовке» |
