## 1. Цель

Стабильное, воспроизводимое **ориентировочное КБЖУ входного набора продуктов до приготовления**.

MVP **сознательно не** определяет пищевую ценность готового блюда (испарение, поглощение масла, слив, выход). Это другой класс задачи — этап 3, `yield_weight_g`, отдельная фраза человека.

Нутриенты хранятся **на `Ingredient`**, не на рецепте. Расчёт — ещё один производный слой после сборки и масштаба (как аллергены display), не второй тип контента в ста JSON.

- детерминированный расчёт **после** сборки варианта и масштаба;
- без runtime-запросов к USDA / любым внешним API;
- без чисел, которые автор вписывает в рецепт;
- в UI явно: «ориентировочно», не лаборатория и не диета.

Не цель этого среза: точная калорийность тарелки, медицинские обещания, фильтр калькулятора «до N ккал».

Цепочка (не параллельная система):

```
Ingredient (аллергены, плотность, нутриенты, веса единиц)
Recipe → assemble (variant → equipment → energy) → scale → nutrition → display
                                                      ├── total
                                                      ├── per_100g_input
                                                      └── per_serving | null
```

## 3. Факт кодовой базы (не менять ради плана)

Сборка display (Django): база → дельта `variant` → дельта `equipment` → дельта `energy` (query пока не принимают) → **затем** масштаб `servings` XOR `anchor_weight`.

На карточке количества после «У меня» считает клиент (`v2/frontend/lib/scale.ts` ≡ Django `services/scale.py`, DEC-021). КБЖУ обязано жить в том же месте: **после тех же scaled amounts**, не `total * ratio` (ломает `gentle` на масле).

`Ingredient` уже: `canonical_id`, `title`, `aliases`, `density_g_per_ml`, три списка аллергенов. Сид имён: `v2/backend/apps/recipes/fixtures/v1_ingredient_map.json` (~140 канонов V1 + заявки оверлея `new_ingredients`).

`RecipeIngredient`: `amount`, `amount_max`, `unit` (VOCAB), `optional`, `scale_mode`, `scalable`, `is_anchor`. Единицы: `g` `kg` `ml` `l` `pcs` `tsp` `tbsp` `pinch` `clove` `bunch` `slice` `to_taste`.

`Recipe.servings` часто `NULL` (V1 ETL не подставляет 4). Якорь — граммы/мл одного продукта, не выход блюда.

`optional: true` уже не входит в аллергены карточки (TESTING U14). Для КБЖУ — то же: опциональное «для подачи» в сумму по умолчанию не входит.

Канон калоража сегодня: VOCAB `energy_profile`, UX-PROPOSAL §6 п.9 «Не писать ккал», RECIPE.md «Не считать ккал», DEFAULTS «БЖУ вне скоупа». HUMAN 2.13 — переключатель обычный/полегче/сытнее, **не** БЖУ.

## 5. Контракт расчёта (спека)

Зафиксировать **до** кода API. Переименовывать `per_100g_*` после появления клиентов дороже, чем сейчас выбрать имя.

### 5.0. Черновик DEC (на этап 0 — в DECISIONS.md)

Рабочий номер: DEC-0XX. Четыре инварианта:

1. JSON рецепта автора не содержит nutrition / kcal / БЖУ.
2. Источник чисел на 100 г — `Ingredient` (сид), не строка рецепта.
3. Источник истины формулы — Django (`services/nutrition.py`), Decimal, после assemble+`apply_mode`.
4. Frontend после `scaleLine` **воспроизводит** ту же формулу по проекции строки. Это не второй источник истины и не API каталога.

Дополнительно в том же DEC: `kcal` суммируется с канонов, не считается Atwater; базис MVP — вход до готовки (`raw_input`).

### 5.1. Когда считать

Вход: **уже собранный** список строк (после дельт) и **уже применённый** `apply_mode` (ratio якоря или порций), **без** `roundScaled`.

Выход висит на display-объекте рецепта, не на строке БД `Recipe`.

Порядок внутри строки:

1. Пропуск, если не входит (§5.4).
2. Граммы из **resolved amount** (§5.2) и unit (§5.3). Нет перевода → строка вне суммы, `incomplete = true`.
3. Вклад = `nutrition_per_100g * grams / 100` (Decimal). `kcal` вклада — из хранящегося `kcal_per_100g`, не из 4/9/4.
4. Сумма вкладов = `total`.
5. `per_100g_input` = `total * 100 / mass_g`, где `mass_g` — сумма грамм строк, учтённых в знаменателе (§5.4). Нет массы → `null`.
6. `per_serving` = `total / servings`, если `servings` целое ≥ 1. Иначе `null`.
7. Отображение: ккал — целое; Б/Ж/У — один знак после запятой (DEFAULTS на этапе 0).

### 5.2. Инвариант количества (ranges)

Nutrition использует **то же resolved display amount**, что и список ингредиентов после `apply_mode`, до округления UI.

Для диапазона `amount` … `amount_max` в MVP nutrition берёт **`amount` (нижняя граница)**. `amount_max` в расчёт не входит.

Нельзя, чтобы соевый соус «1–2 ст. л.» в одном месте считался по 1, в другом по середине или по 2. Другое правило (середина / max) — только новая фраза человека и правка канона.

`pinch` / `to_taste`: `amount` уже `NULL` по DATA-MODEL — в КБЖУ не переводятся (§5.4), это не incomplete справочника.

### 5.3. Граммы

`g_per_tsp` / `g_per_tbsp` / `g_per_pcs` / `g_per_clove` / `g_per_bunch` / `g_per_slice` — **редакционная оценка типовой массы единицы этого канона**, не физическая константа. Яйцо ≈ 50 г, луковица ≈ 100 г, зубчик чеснока ≈ 5 г — осознанная оценка, как типовой `hard_cheese`.

Нет своего `g_per_*` у нужного unit → `incomplete`, строка вне суммы. **Запрещено** подставлять глобальную таблицу ложек.

| unit | граммы | Если данных нет |
|------|--------|-----------------|
| `g` | `amount` | — |
| `kg` | `amount * 1000` | — |
| `ml` | `amount * density_g_per_ml` | `incomplete`, строка вне суммы |
| `l` | `amount * 1000 * density_g_per_ml` | то же |
| `tsp` `tbsp` `pcs` `clove` `bunch` `slice` | `amount * g_per_<unit>` этого канона | то же |
| `pinch` `to_taste` | не переводятся | не incomplete из-за единицы |

Плотность мл/л: `Ingredient.density_g_per_ml`. Нет плотности у жидкой строки = incomplete, не «как вода».

Вода: `density_g_per_ml = 1`, нутриенты нули. В супе строка воды **в знаменателе** `per_100g_input` (это масса входа, не выход кастрюли).

### 5.4. Что входит: целиком или никак

По умолчанию входит всё обязательное, что переводится в граммы.

Не входит **ни в числитель КБЖУ, ни в массу `per_100g_input`**:

- `optional: true`;
- `unit` ∈ `to_taste` \| `pinch`;
- `nutrition_exclude: true`.

`nutrition_exclude=true` значит только это. Не «частично съедается». Частичность = `nutrition_factor`, его в MVP нет.

Входит в массу, макросы нули (не exclude): вода / бульон, которые **остаются** в блюде (суп, рагу, каша).

Масло в съедаемом маринаде: входит целиком. Масло «для жарки» в MVP: **входит целиком**, пока редакция не поставила `nutrition_exclude`. Не ставить 0.5.

`choice_group`: выбранная ветка display, не среднее.

Нет нутриентов на каноне или нет граммов: строка вне суммы, `incomplete = true`. Не выдавать нули как точный расчёт.

`pinch` / `to_taste` **не** делают `incomplete`. Они просто не в сумме. Это не ошибка справочника.

Редакционное (RECIPE.md, этап 0): **нельзя** ставить `to_taste` / `pinch` на ингредиент, существенный по калорийности (масло, майонез, сметана, сливки, сахар, орехи…). Валидатор: известные жирные/сладкие каноны + `to_taste`/`pinch` → ошибка, не молчаливый 0 ккал.

### 5.5. Имена в API (зафиксировать сейчас)

Не называть поле `per_100g` или `per_100g_raw`. `raw` через полгода прочитают как «100 г блюда / сырая порция готового».

```json
"nutrition": {
  "basis": "raw_input",
  "incomplete": false,
  "total": { "kcal": 1840, "protein_g": 112.0, "fat_g": 126.0, "carbs_g": 48.0 },
  "per_100g_input": { "kcal": 214, "protein_g": 13.0, "fat_g": 14.7, "carbs_g": 5.6 },
  "per_serving": null
}
```

| Поле | Смысл |
|------|--------|
| `basis` | В MVP всегда `"raw_input"`: набор продуктов **до** готовки. Не готовое блюдо. |
| `total` | Сумма по учтённым строкам текущего display (после дельт и масштаба). |
| `per_100g_input` | `total` на 100 г **входной** учтённой массы. Не 100 г тарелки. |
| `per_serving` | Только если есть `servings`; иначе JSON `null`. |
| `incomplete` | Хотя бы одна обязательная строка не вошла из-за дыры справочника или единиц. |

UI: «на 100 г продуктов (до готовки)», никогда «на 100 г блюда».

`yield_weight_g` / `per_100g_cooked` — не в этом срезе. Когда появятся — **новые поля**, не переименование `per_100g_input`.

### 5.6. Клиент «У меня» — проекция, не второй API

Нельзя отдать один `total` и умножить на ratio.

**A (канон этого черновика):** Django на **каждой display-строке** карточки отдаёт минимум для воспроизведения после `scaleLine`. Это проекция расчёта, не справочник Ingredient наружу и не контракт других экранов.

Рекомендуемая проекция строки (ровно для этой `unit`, уже разрежённая):

```json
{
  "amount": 2,
  "unit": "tbsp",
  "nutrition_line": {
    "kcal_per_100g": 884,
    "protein_g_per_100g": 0,
    "fat_g_per_100g": 100,
    "carbs_g_per_100g": 0,
    "grams_per_unit": 14
  }
}
```

- `nutrition_line: null` — строка не участвует (exclude / optional / pinch / to_taste / нет данных). Клиент не считает.
- `grams_per_unit` — граммы **одной** текущей единицы этой строки (`tbsp`→14, `g`→1, `ml`→density). Не пачка `g_per_tsp`+`g_per_tbsp`+density.
- Клиент: `grams = apply_mode(amount) * grams_per_unit`, затем вклад как Django. Без `roundScaled` до вклада.
- Каталог, калькулятор, другие страницы этот объект **не** читают. Нет отдельного `/api/nutrition`.

**B:** fetch на шаг слайдера — запрещён (DEC-021).

Клиент не ходит в USDA и не подставляет глобальные ложки.

## 6. Данные

### 6.1. Поля `Ingredient` (предложение в DATA-MODEL *позже*, до этапа 0 не создавать)

Нутриенты — колонки той же таблицы `Ingredient` (рядом с аллергенами и `density_g_per_ml`), не отдельная сущность.

Базис в MVP **один**, enum не text:

`nutrition_basis = raw_100g`

Числа — на 100 г **типового сырого продукта в том виде, как он в рецепте** (гречка сухая, не каша; грудка сырая, не запечённая). Значений `cooked_100g` / `prepared_100g` в MVP нет. Появятся — расширение enum + миграция, не свободная строка.

| Поле | Тип | Null | Смысл |
|------|-----|------|--------|
| `kcal_per_100g` | decimal | да | энергия **источника**, не Atwater |
| `protein_g_per_100g` | decimal | да | |
| `fat_g_per_100g` | decimal | да | |
| `carbs_g_per_100g` | decimal | да | как в источнике; сахар отдельно не в MVP |
| `nutrition_basis` | enum | нет, если нутриенты есть | в MVP только `raw_100g` |
| `nutrition_source` | enum, nullable | да | `fooddata_central` \| `ru_table` \| `packaging_typical` \| `editorial` |
| `nutrition_source_id` | text | да | только если у источника есть устойчивый id (FDC). У `editorial` обычно `null` |
| `g_per_tsp` … `g_per_slice` | decimal | да | типовая масса единицы **этого** канона |

Четыре макроса + kcal: все заполнены или все null. Валидатор сида.

`nutrition_source_id` **не** обязателен. Правило: заполнять, когда id стабилен; не выдумывать ключ для editorial.

Не плодить каноны ради жира отруба: `beef` — одно типовое значение. Расхождение — дисклеймер, не второй id без нужды.

### 6.2. Флаг на строке рецепта

`nutrition_exclude: bool`, дефолт `false`. Нет ключа = false.

Смысл только §5.4: строка целиком вне числителя и вне массы. Валидатор: boolean. Не 0.5, не «почти».

Автор оверлея не обязан разметить все 43 вместе со справочником: без флага масло жарки входит целиком (верхняя оценка).

Этап 2b (не блокирует карточку): эталон + супы/жарки, exclude где жидкость сливают.

### 6.3. Сид, не рантайм

Файл: `v2/backend/apps/recipes/fixtures/ingredient_nutrition.json`.

Ключ — `canonical_id`. Значение — четыре числа + kcal, `nutrition_source`, опционально `nutrition_source_id`, веса единиц, плотность если ещё нет.

Скрипт **одноразовый** (dev, не Celery, не Next, не прод):

1. Редакционная карта `canonical_id → fdc_id` (модель не угадывает).
2. Выгрузка FDC с машины разработчика → JSON.
3. JSON в git.

Лицензия FDC: CC0 — в README сида. Молочка/колбаса РФ: `ru_table` / `editorial` / `packaging_typical`, не USDA sour cream.

Карта FDC: один id, форма raw / SR Legacy или Foundation, не branded. Нет матча — null на каноне, `incomplete` на блюде. Не подставлять «курицу вообще» в `chicken_breast`.

### 6.4. Охват и UI неполноты

Сначала каноны из принятых оверлеев + V1 map. Не вся FDC.

`incomplete` — булев факт расчёта, не эвристика «якорь закрыт». Нет порога «показали, потому что есть белок».

Политика UI MVP (рекомендация; HUMAN §11):

- `incomplete: false` — обычный блок «ориентировочно»;
- `incomplete: true` — тот же блок чисел **и** заметная пометка «неполный расчёт» (не мелкая серая строка). Число без этой пометки пользователь примет за почти точное.

Скрывать блок при `incomplete` — альтернатива строже; дольше без пользы. Не выбирать «показывать если есть мясо».
