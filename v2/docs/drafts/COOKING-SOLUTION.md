## Вердикт

Текущий `/calculator` — умный фильтр с рангом. Это честно описано в CALCULATOR.md: жёсткий отсев + совпадение чипов (+10 / +4 / +2) + «почему» из тех же чипов. Рецепт под человека не собирается. Карточка ведёт на `/recipes/<slug>` **без** `variant` / `equipment` из подбора.

Идея «несколько заранее написанных JSON на блюдо» — нет. Комбинаторный взрыв. Уже принято иное: один `Recipe.slug` + дельты `RecipeVariant` (DEC-012, оси addon / equipment / energy).

Ядро продукта, если калькулятор должен «выстрелить»:

```
ситуация человека
  → база блюда
  → допустимая адаптация
  → CookingSolution (конкретная версия + объяснение)
```

Не «какие рецепты подходят», а «какой ужин из базы сейчас лучше собрать».

Runtime LLM нет (DEC-004). Правила, граф замен, тексты «почему» — заранее в данных. В рантайме — Django + Postgres, детерминированно.

## Что уже есть (не ломать)

Четыре слоя из обсуждения почти совпадают с кодом. Не хватает третьего на выдаче и настоящего четвёртого.

| Слой | Сейчас | Дыра |
|------|--------|------|
| 1. Нельзя | unpublished, аллерген `contains`/`unknown`, нет основы/способа/посуды | ок для среза |
| 2. Найти основу | семейство, один slug на карточку | ок |
| 3. Адаптировать | `assemble`: база ⊕ addon ⊕ equipment ⊕ energy, потом масштаб | калькулятор **не выбирает** ось; клик открывает базу |
| 4. Оценить | `score_and_why` только по выбранным чипам | нет трения, покупок, качества замены |

`energy_profile` — заготовка оси, не три отдельных блюда. Не плодить десять профилей. Оси разные: энергия ≠ время ≠ усилие ≠ метод (это уже в VOCAB / сборке).

Кладовка и «докупить» в каноне — **V2.2** (HUMAN 9.3, DEC-015). Этот черновик **предлагает** сдвинуть простой pantry раньше — это вопрос человеку, не тихая правка PLAN.

## Целевые объекты (код, не UI)

Не переименовывать пункт шапки, пока HUMAN 3.15 пуст. В движке:

```
Recipe  →  Candidate  →  AdaptationPlan  →  CookingSolution
```

`CookingSolution` — то, что выдаёт калькулятор вместо «семейство совпало»:

| Поле | Смысл |
|------|--------|
| `recipe` | slug семейства |
| `applied_axes` | выбранные addon / equipment / energy |
| `substitutions[]` | канон → канон, с `quality` |
| `omissions[]` | что можно не класть |
| `servings` / якорь | если когда-нибудь считаем объём |
| `shopping_delta` | чего нет (сначала список имён, потом граммы) |
| `score` | внутренний, **не** в UI |
| `reasons[]` | русские «почему» |

Пользователю не показывать `0.87342`. Показывать:

- можно приготовить сейчас / нужно 1 имя / лучше, если купить;
- что совпало (основа, посуда, время);
- что заменили;
- чего не хватает.

Три корзины выдачи (сейчас / минимум покупок / лучший результат) имеют смысл **только** когда есть слой «что есть дома». Без него это снова те же чипы.

## Этапы (предложение в PLAN, не команда сессии)

### 0 — добить спринт 2

Как в CURRENT_SPRINT. Калькулятор остаётся фильтром. Это слой 1–2.

### A — мост без кладовки (тонкий спринт после приёмки 2)

Калькулятор отдаёт **версию**, не только семейство.

- При фильтре способа/посуды выбрать подходящий `RecipeVariant` (`cook_method_override`, `axis=equipment`).
- Карточка ведёт на `/recipes/<slug>?equipment=&variant=`.
- «Почему» говорит про выбранную ось («духовка — вариант посуды», не только «совпал метод»), если матч через дельту.
- Внутренний тип `CookingSolution` с пустыми substitutions / shopping.

Контент: не выдумывать дельты у 43. Где `has_delta=false` — по-прежнему база + свёртка.

Это уже ощущается как «подобрал способ приготовить», а не как каталог с чипами.

### B — простой pantry (вопрос: раньше V2.2?)

Без граммов, без аккаунта, чипы или короткий список в URL:

«Есть: курица · лук · гречка»

Движок: обязательные ингредиенты display-состава (после сборки варианта) vs список «есть».

Выдача человеческая, не «совпало 75%»:

- можно сейчас;
- не хватает 1 названия;
- замена разрешена (если граф уже есть).

Граммы, остатки, срок, корзина — позже, как в PLAN V2.2.

Без этого шага большая часть «стоимости приготовления» не работает. С ним фильтр становится decision engine.

### C — граф замен и трение

Offline (волны / модератор, не рантайм):

- замена в **контексте блюда**, не глобально «сливки → вода»;
- `quality` 0…1, ниже порога — запрет;
- пропуск optional не штраф.

Ранг внутренний (не один процент в карточке):

`food + preference + equipment + time − shopping_friction − cooking_friction`

Friction: сколько не хватает, сколько замен, посуда, активные шаги, редкий канон, спецтехника. Числа — DEFAULTS, золотые pytest.

Оси усилия/времени — поля рецепта или дельты, не десять energy-профилей.

### D — три стратегии в UI

Когда B живёт:

- сейчас (всё есть, низкое трение);
- почти (1–2 имени);
- лучше, если купить / готовить дольше.

Не три случайных разных блюда из алфавита.

## Данные: дельты, не клоны

Хранить как сейчас, наращивать правила, не размножать slug.

```
Recipe                  база
RecipeVariant           именованные оси (уже есть)
SubstitutionRule        позже: from, to, context, quality, forbidden
AdaptationRule          позже: when {equipment, time_max, without} → changes
```

`when` + `changes` — это те же дельты, что `RecipeVariant`, плюс условие «когда калькулятор имеет право применить». Не второй каталог рецептов.

Автор (Grok) / модератор (Luna) после «стартуй волну 1» пишут дельты и граф. `editorial_tested` по-прежнему только человек.

## Как проверить, что это не фильтр

Фильтр: «птица + духовка» → список семейств, клик открывает базу на сковороде.

Сборка: та же пара → карточка уже с осью духовки, «почему» про эту ось, состав на странице тот же, что обещала карточка.

Когда появится pantry: «есть курица и гречка» → не «8 рецептов с курицей», а одно решение с объяснением, чего не хватает или что заменено.
