# Черновик: семейство на одном slug, посуда, заметки

Статус: **перенесён в канон 2026-09-05.** Не править этот файл — править [VOCAB.md](../VOCAB.md), [DATA-MODEL.md](../DATA-MODEL.md), [API.md](../API.md), [DECISIONS.md](../DECISIONS.md) DEC-012…015. Задача сессии: [../../CURRENT_SPRINT.md](../../CURRENT_SPRINT.md).

Ниже — архив предложения. Расхождения с каноном решаются в пользу канона.

Принято в чате (2026-09-05), уже можно опираться:

- HUMAN **9.1**: вариации = **дельты**, **один** `Recipe.slug`, не семья из нескольких карточек.
- HUMAN **9.2**: посуда — **отдельная ось**, **отдельный переключатель** рядом с добавками. Не второй slug. Не смешивать «с грибами» и «в казане» в один список.
- HUMAN **9.5**: первый уровень книги — `protein_base`.
- HUMAN **9.3**: калькулятор **этого** спринта **без** кладовки и «докупить».
- HUMAN **9.4**: отрубы — **фильтр** книги/калькулятора и поле **на базе** рецепта, не чип вариации семейства. Имена в UI — бытовые РФ (голяшка, лопатка, шея), не англо-стейковые.
- HUMAN **9.6**: квоты заметок — когда делают рецепт, не отдельным проходом по 43.
- Масштаб якоря «У меня» — **после** выбранного варианта (как после `energy_profile` в VOCAB). Порции не выдумывать: у V1 `servings` нет, ETL **не** подставляет 4.

Срез факта (код, не цель): `Recipe.variations` — JSONField `[{title, text}]`; `Recipe.notes` — TextField-blob. `energy_profile` на карточке всегда `standard`. `RecipeStep.equipment_note` уже есть. `editorial_tested` агент не ставит. `scale_mode=fixed` нет (это `scalable=false`).

## 1. Модель семейства: одно тело, варианты-дельты

Одна строка `Recipe`, один `slug`, один URL `/recipes/<slug>`. В книге это **одна** карточка. Переключатель на странице меняет **display-состав** (ингредиенты, шаги, аллергены, high-risk, при необходимости `cook_method`), не создаёт второй id.

База (`base`): то, что сейчас лежит в `RecipeIngredient` / `RecipeStep` / флаги / `caution_text`. Это и есть вариант «как в заголовке», без добавок.

Вариант: именованная **дельта** к базе (образец — VOCAB `energy_profile`: `light`/`rich` не второй slug, а дельта количеств и шагов + `allergen_delta`).

### Три оси (посуда отделена от добавок — 9.2)

Разные вопросы к одному блюду, **разные переключатели**. Пустая ось → блока нет. Добавки и посуду в один ряд чипов не смешивать.

| Ось | Поле / ключ | Вопрос | Коды | Пример |
|-----|-------------|--------|------|--------|
| Добавка | `variant` (`axis=addon`) | Что положить сверх базы? | свободный `id` рецепта | база / с грибами / с пармезаном |
| Посуда | `equipment` (`axis=equipment`) | В чём готовим? | VOCAB §3 ниже | кастрюля / духовка / казан |
| Калораж | `energy` (`axis=energy`) | Насколько жирно, тот же вкус? | VOCAB: `standard` \| `light` \| `rich` | обычный / полегче / сытнее |

Почему не две оси: «с грибами» меняет состав и вкус-гарнир; «полегче» — редакционный жир/сахар **того же** блюда (VOCAB: не подменять стейк курицей); «казан» — сосуд и часто время/жидкость. Склеить «грибы» и `light` в один список чипов — путаница для UI и для автора.

Скаляр `Recipe.energy_profile` среза (`standard`) остаётся **дефолтом оси energy**, не отдельной карточкой. UI калоража по-прежнему не в срезе 1, пока человек не закроет HUMAN 2.13 / 9.x.

`protein_base`, `dish_type` и отрубы (`allowed_cuts`, §3a) у семейства **не** оси варианта: «голяшка» не чип жаркого. `cook_method` на `Recipe` — метод **базы**; ось посуды (9.2 принято) может дать `cook_method_override` (`boil` vs `oven` — то же семейство, другой переключатель).

### Порядок сборки display (Django, не Next)

1. Тело базы.
2. Дельта `variant` (addon), если выбрана и `has_delta=true`.
3. Дельта `equipment`, если выбрана и не совпадает с дефолтом базы.
4. Дельта `energy`, если не `standard`.
5. **Затем** масштаб: `servings` **или** `anchor_weight` (оба сразу — 400). `ratio` от **уже собранного** якоря. Нет `servings` и нет якоря после сборки → `scaling.enabled=false`, количества display без ratio. Не подставлять 4 порции.

Таймеры, `pull_*` / `target_*`, `hold_seconds` не умножаются. `gentle` = `ratio^0.7`. `scale_mode` только `linear` \| `gentle` \| `whole` \| `manual`; фиксированное количество — `scalable=false`.

### Инварианты

**Аллергены варианта.** Источник правды — каноны строк **после** сборки. Любая дельта с `ingredient_delta` обязана нести `allergen_delta` (SAFETY). Валидатор: объединение `allergens_*` канонов display должно совпасть с «база ⊕ allergen_delta». Расхождение — ошибка публикации, не молчаливый union. `unknown` нельзя превратить в «нет». На карточке каталога — см. §5 (худший случай vs база).

**High-risk.** Display-флаги = база ∪ `high_risk_delta.add` ∖ `high_risk_delta.remove`. Вариант с флагом и статус `published` → нужен `caution_text` базы или `caution_text_override` варианта. Агент не ставит `editorial_tested`.

**Якорь `is_anchor`.** После сборки **не больше одной** строки `is_anchor=true`. Предложение по умолчанию: флаг живёт на **базовом теле**; добавки (грибы, пармезан) якорь не трогают; `replace` якорной строки **наследует** якорь, если вариант явно не снял его. Вариант **может** объявить свой якорь, только если заменяет якорный продукт (V1-смысл: «вместо рибая — тонкая лопатка»). Снять якорь и не поставить новый при `servings IS NULL` → масштаб выключен (это норма, не 4 порции). Открытый вопрос — §7.

**Один slug.** Нет `family_id`, нет редиректа «кабачок → другой рецепт», нет четырёх карточек жаркого в `/recipes`.

**Каталог.** Ось книги — `protein_base`. Фильтры метода и посуды смотрят на **доступные** оси семейства (база ∪ варианты с дельтой). Отрубы — фильтр по полю базы, не по дельтам. Не плодить строки выдачи.

## 2. Схема дельты

Варианты — массив на рецепте (логика; таблица vs JSONField — после принятия, не в этом файле).

```text
RecipeVariant
  id                  slug внутри рецепта, стабильный ключ query (with_mushrooms)
  axis                addon | equipment | energy
  title               русская подпись чипа
  has_delta           bool — false = только legacy-текст, состав не врать
  legacy_text         text, да — V1 title+text, пока нет дельты
  ingredient_delta    объект или нет
  step_delta          объект или нет
  allergen_delta      объект; обязателен, если есть ingredient_delta
  high_risk_delta     { add: VOCAB[], remove: VOCAB[] }
  cook_method_override   VOCAB cook_method или нет
  equipment           VOCAB equipment; только axis=equipment (и дефолт на Recipe)
  caution_text_override  text или нет
  notes_delta         позже; не в первом проходе
```

На одном рецепте: не больше одного варианта с данным `(axis, id)`. Ось energy: `id` ∈ `light` \| `rich` (`standard` = отсутствие дельты). Ось addon: взаимоисключающие чипы (база + ровно один `id`) — пока человек не разрешит комбинации «грибы **и** пармезан» (§7).

### `ingredient_delta`

| Операция | Смысл |
|----------|--------|
| `add` | новые строки как у `RecipeIngredient`: `canonical_id`, `amount` (null для `to_taste`/`pinch`), `amount_max`, `unit`, `detail`, `scale_mode`, `scalable`, `display_name`, `choice_group`; `position` — куда вставить |
| `remove` | ссылки на строки базы: `canonical_id`, если он в базе один; иначе `position` |
| `replace` | та же ссылка + поля патча (часто только `amount` / `detail`) |

Нет `scale_mode=fixed`. Якорь в `add` только по правилу §1.

### `step_delta`

| Операция | Смысл |
|----------|--------|
| `replace` | `position` шага базы + поля (`text`, таймер, температуры, `equipment_note`, …) |
| `insert` | `after_position` (0 = перед первым) + тело шага |

`remove` шага **не** в первом проходе (в ТЗ не было). Переписать шаг целиком — через `replace`. Если посуда выкидывает целый этап — `replace` текста на короткий переход или открытый вопрос про `remove`.

Температуры в дельте шага — те же инварианты SAFETY: `pull` без `target` нельзя. Птица/свинина/фарш — минимумы не ниже канона.

### `allergen_delta`

```text
contains_add / contains_remove
may_contain_add / may_contain_remove
unknown_add / unknown_remove
```

Коды — 14 из VOCAB. Пустые массивы можно опустить, сам объект — нет, если состав менялся.

### Пример: жаркое из говядины (выдуманный контент для схемы, не волна)

База (якорь — говядина; `cook_method=stew`; дефолт `equipment=pot`; `energy` = standard; `servings` нет):

- говядина 800 г (`is_anchor=true`, `linear`)
- лук, морковь, бульон, масло, соль (`gentle`), перец (`gentle`)

**Аддон `with_mushrooms` («С грибами»)**

- `add`: шампиньоны 200 г, `linear` (whitelist SAFETY → не `wild_mushrooms`)
- `insert` после шага пассеровки овощей: обжарить грибы отдельно, не солить сразу
- `allergen_delta`: пустые add/remove (состав без новых кодов 14)
- high-risk не трогать

**Аддон `with_parmesan` («С пармезаном»)**

- `add`: пармезан 40 г, `gentle` или `linear` по RECIPE волны; `scalable=true`
- `insert` в конец: снять с огня, вмешать сыр (не кипятить)
- `allergen_delta.contains_add`: `milk`
- high-risk не трогать

Переключение чипа сразу отдаёт уже собранный `ingredients[]` / `steps[]` / `allergens`. «У меня» 800→1000 г считается **после** грибов: 200 г грибов × ratio, соль `gentle`.

Текстовый V1 вроде голяшек «С грибами» / «С черносливом» **без** этой схемы остаётся `has_delta=false` — см. §6.

## 3. Посуда (`equipment`)

HUMAN **2.5** пуст. Список ниже — предложение в VOCAB, **короткий**, только сосуд/камера. Не нож, не доска, не мультиварка, не микроволновка (VOCAB уже сказал: мультиварка/СВЧ — оборудование, не метод; в этот enum не раздувать, пока нет блюд).

| Код | В UI | Бытовой смысл |
|-----|------|----------------|
| `pot` | Кастрюля | Плита, крышка, суп/варка/тушение |
| `oven` | Духовка | Камера духовки (не путать с методом: query-ключ другой) |
| `kazan` | Казан | Толстые стенки, плов/томление |
| `skillet` | Сковорода | Открытая жарка, соте |
| `saucepan` | Сотейник | Высокие борта, соус/рисоtto |
| `baking_dish` | Форма | Форма / жаровня в духовке |
| `grill` | Гриль | Решётка, мангал, электрогриль как сосуд |

Коды `oven` и `grill` **совпадают** с `cook_method` по написанию — это разные словари: `?cook_method=oven` vs `?equipment=oven`. В JSON всегда ясно по имени поля.

Черновики метода `air_fryer` / `deep_fry` — **не** дублировать здесь чашей, пока нет оси.

### Связь с `cook_method`

| | `cook_method` | `equipment` |
|--|---------------|-------------|
| Вопрос | Как готовим (жарка / тушение / варка) | В чём лежит еда |
| Каталог | фильтр способа | фильтр посуды (после основы и метода — HUMAN 9.5) |
| Дефолт | поле `Recipe.cook_method` | поле `Recipe.equipment` (предложение; сейчас в каноне нет) |

Типичные пары, не CHECK: `pan_fry`→`skillet`; `boil`→`pot`; `stew`→`pot` или `kazan` или `oven`+`baking_dish`; `oven`→`oven` (+часто `baking_dish`); `grill`→`grill`; `no_cook`→ поле пусто.

Смена кастрюля → духовка у **того же** жаркого: ось equipment, отдельный чип (не в списке «с грибами»), при необходимости `cook_method_override=oven`. В книге по-прежнему один slug (9.2 принято).

### Когда дельта посуды, когда `equipment_note`

**Ось / дельта `equipment`**, если меняется сосуд и из‑за этого время, объём жидкости, крышка, или метод (`stew` на плите vs та же сборка в духовке). Чип на рецепте и фильтр в книге/калькуляторе.

**`RecipeStep.equipment_note`** (уже в DATA-MODEL): тот же сосуд, предостережение в шаге («не перегружать сковороду», «крышка с отверстием»). Переключателя нет.

Правило автора: «можно и в сотейнике, минуты те же» → note или одна фраза в заметках, **не** вторая ось. Два осмысленных пути (казан 40 мин vs духовка 2.5 ч) → дельты.

Калькулятор спринта (принятое 9.3): основа + метод + посуда, без граммов кладовки. Отрубы — углублённый фильтр после основы (9.4), не ось семейства. Пустые ниши — empty-state, не гид «скоро».

## 3a. Отрубы — поле базы, не ось семейства

HUMAN **9.4 принят** как продуктовый жест (фильтр, не чип вариации). Словарь кодов **ещё не в VOCAB** — этот абзац предложение для HUMAN 2.x, не переносить в DATA-MODEL.

Не путать с `/api/guides/meat/<cut>/`, где `cut` ∈ `beef` \| `pork` \| `poultry` (вид гида, не отруб).

| Что | Не что |
|-----|--------|
| Массив на **базе** `Recipe` | Чип «голяшка» у жаркого рядом с «с грибами» |
| Фильтр книги и калькулятора (после `protein_base`) | `axis` у `RecipeVariant` |
| Бытовые имена РФ в UI | Англо-стейк (ribeye, chuck roll) как подпись чипа |

**Имя поля.** Рекомендация: `allowed_cuts` на `Recipe` (допустимые части **этого** блюда). Query каталога короче: `cuts=` (как фильтр, OR внутри ключа). Не `cut=` — занято гидом мяса.

Тип: массив кодов VOCAB, когда словарь появится. Несколько значений — «лопатка или огузок» у одного рецепта, не два slug.

**Коды vs русские строки (пока нет VOCAB).** Рекомендация как у `protein_base`: код латиницей + `title_ru` в словаре. В публичном API и в query — **только коды**. Свободные русские строки («голяшка», «голяшки») в JSON/фильтре **запрещены**: иначе ETL и 400/ignore разъедутся.

До появления таблицы в VOCAB:

- HTTP: неизвестный `cuts=` → **400**; поле на карточке не отдавать русским массивом.
- ETL 43: `allowed_cuts: []`, не угадывать из title.
- Временно русские `labels` — только в packet автору / админке, не в API. Альтернатива «labels temporarily в API» — **не** рекомендуем.

Полную карту мясника не выдумывать. Набросок для HUMAN 2.x (бытовые РФ; UI = `title_ru`). Код общий при том же слове, вид мяса — из `protein_base`.

| Код (черновик) | title_ru | Где уместен |
|----------------|----------|-------------|
| `shank` | голяшка | говядина, баранина |
| `shoulder` | лопатка | говядина, свинина, баранина |
| `neck` | шея | говядина, свинина |
| `rump` | огузок | говядина |
| `brisket` | грудинка | говядина; свинина — уточнить в 2.x |
| `thick_rib` | толстый край | говядина (не подпись «рибай») |
| `tenderloin` | вырезка | говядина, свинина |
| `loin` | корейка | свинина |
| `belly` | брюшина | свинина |
| `ribs` | рёбра | свинина |
| `mince` | фарш | все три |
| `breast` | грудка | птица |
| `thigh` | бедро | птица |
| `drumstick` | голень | птица |
| `wing` | крыло | птица |
| `whole_bird` | целиком | птица |

Рыба/овощи (сорт, «часть») — тот же приём позже, не этот массив. Оссобуко: `protein_base=beef`, `allowed_cuts=[shank]`; на странице чипы — грибы и казан, не «голяшка».

**Квоты 9.6** (заметки) к отрубам не относятся. Разметка отрубов — в RECIPE, когда делают/перерабатывают рецепт, не отдельным проходом по 43.

## 4. Заметки: массив, не blob

Предложение поля (канон `notes` text пока не трогать):

```text
notes: [{ "title": string | null, "text": string }, ...]
```

`title` может быть пустым (ETL V1). `text` обязателен, не пустая строка. UI — список пунктов 0…10, не простыня (UX претензия 5).

**Квоты min 3 / avg 6 / max 10** — контент [RECIPE.md](../RECIPE.md) для волн / переработки семейства (9.6 принято), не CONSTRAINT/CHECK в Postgres, не валидатор импорта 43. Текущие 43 агент **не** дописывает отдельным проходом.

`editorial_tested` к заметкам не привязывать.

### ETL V1 (`notes` blob → массив)

| Вход | Выход |
|------|--------|
| `NULL` / только пробелы | `[]` |
| нет разделителя `\n\n` | один пункт `{ "title": null, "text": "<blob>" }` |
| есть `\n\n` | нарезка по `\n\n`, trim, пустые куски выбросить; у каждого `title: null` |

Не выдумывать заголовки из «Сухая поверхность: …» и не выкидывать блок «Пилот sol-chef». HTML из V1 notes не обещать. Если нарезка дала >10 пунктов — импорт не режет (квота не CHECK); в UI волны потом правят. Срез 43 так не раздувается.

`variations` V1 в заметки **не** переносить.

## 5. API рецепта — набросок (не правка API.md)

`GET /api/recipes/<slug>/` сегодня: `servings` XOR `anchor_weight`; `variations: [{title,text}]`; `notes: "…"`.

Предложение query (имена ключей = оси):

| Query | Смысл | Нет / неизвестно |
|-------|--------|------------------|
| `variant=` | `id` оси addon | нет ключа = база; чужой id → **400** |
| `equipment=` | код VOCAB посуды | нет ключа = `Recipe.equipment` базы; чужой код → **400**; код не из доступных этого рецепта → **400** |
| `energy=` | `light` \| `rich` | нет ключа = `standard`; в срезе 1 по-прежнему можно не принимать (как сейчас «нет `?energy=`») |
| `cuts=` | код отруба (каталог / калькулятор, не карточка) | нет ключа = не фильтровать; чужой код → **400**; пока нет VOCAB — ключ не принимать |
| `servings=` / `anchor_weight=` | как сейчас, **после** дельт | оба → 400 |

Не класть вариант в path (`/recipes/<slug>/with_mushrooms`) в первом проходе — ломает HUMAN 3.3 (`/recipes/<slug>`). Шаринг: те же query, что калькулятор. Открытый вопрос — §7.

Тело (добавки к текущему JSON, имена английские):

```text
applied: { variant: null | id, equipment: code | null, energy: standard|light|rich }
available_variants: [{ id, title, axis, has_delta }]
available_equipment: [codes]
allowed_cuts: [codes]               база; не зависит от variant/equipment
ingredients / steps / allergens     уже собранный display
notes: [{ title, text }]            не строка
variations:                         только legacy has_delta=false, чтобы UI не врал
scaling                             ratio от якоря display
```

Каталог `GET /api/recipes/` и рекомендации: плюс фильтр `equipment=` (OR внутри ключа, AND с `protein_base` / `cook_method`) и `cuts=` (OR; попадание — код ∈ `allowed_cuts` базы). Посуда: код есть у базы **или** у варианта с `has_delta`. Одна строка результата на slug. `variant=` / `equipment=` на карточке — переключатели осей; `cuts=` на карточке **нет** (это не display-дельта).

Аллергены **карточки** каталога: предложение — **объединение базы и всех addon/energy с дельтой** (`contains` и `unknown`), чтобы «без молока» скрыло жаркое, у которого есть чип пармезана. Страница рецепта показывает аллергены **текущего** display. Человеку решить, не молчать.

Калькулятор спринта: те же словари, без `/api/pantry/`, без «докупить».

## 6. Миграция 43 V1

Источник: `variations[]` как в [docs/ADD_RECIPE.md](../../../docs/ADD_RECIPE.md) — только `title` + `text` (иногда HTML). Дельт нет. Не выводить `light`. Не ставить якорь «на глаз» сверх уже сделанной эвристики ETL. Не ставить `editorial_tested`.

Запись после импорта:

```text
{
  "id": "<slug из title>",
  "axis": "addon",
  "title": "С грибами",
  "has_delta": false,
  "legacy_text": "<как в V1>",
  "ingredient_delta": null,
  "step_delta": null
}
```

`Recipe.equipment` на ETL: грубый дефолт из папки/`cook_method` (`skovoroda`→`skillet`, `kastryulya`→`pot`, `duhovka`→`oven`, `tushenie`→`pot`, `grill`→`grill`) — **без** оси вариантов посуды. Казан vs форма не угадывать.

**UI:** переключатель состава рисуется только если `has_delta=true`. Иначе жест V1: свёртка «Вариации» с текстом, список ингредиентов подписан как база. Нельзя подсветить «С грибами» и показать те же 800 г говядины так, будто грибы уже в составе.

Волны RECIPE: минимум одна variation как **дельта**, не второй рецепт (уже в RECIPE.md). 43 не конвертировать в дельты без волны / без фразы «стартуй волну».
